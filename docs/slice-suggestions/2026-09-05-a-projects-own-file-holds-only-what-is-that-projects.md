# A project's own file holds only what is that project's

**Found by:** the lane on card #54 (docs/plans/2026-09-05-18-a-new-project-follows-the-way-we-work-on-any-machine-and-teaches-it-back.md), in the walk of HOW-WE-WORK as its readers would read it, from the owner's words on 2026-09-05: "my doctrine has drifted in different projects and I want Needle to be the one true doctrine. Then there are project specific properties that might need to survive, but operating doctrine comes from Needle."
**Kind:** defect
**Fix:** his

## Observation

Card #54 collapses two of the three places the doctrine lives: `docs/HOW-WE-WORK.md` and the machine's global `~/.claude/CLAUDE.md`, one row per paragraph, by the owner's ruling. The third place is every project's own `CLAUDE.md`, and the card does not read them. Codex's note of 2026-09-05 (`from-claude-shared-organisation-prerequisite.md` §4) already observed that Hello Revenue's `CLAUDE.md` restates doctrine paragraphs in its own words; Needle's own says "this file holds only what is true of Needle" and then carries a paragraph on the review rings that HOW-WE-WORK §11 also carries. Nothing reads a project file against the one text, so the same rule can exist in three wordings and drift in each, which is the state #54 exists to end for two of them.

The first cross-make conversation after #54 exposed the other, more expensive
direction. Hello Revenue's `CLAUDE.md` is the product of roughly twelve months
of close work between the owner and Claude, only about five months of which is
visible in that repository's Git history. It contains operational distinctions
HOW-WE-WORK does not currently make: what counts as ground truth; that training
recall and in-session memory are not ground truth; epistemic status on
load-bearing claims; a hedge as a trigger to verify; the naming impulse as the
moment to search for an existing primitive; and that the search obligation
binds a plan before it binds execution. Codex reproduced the first class and
then proposed a new communication mechanism before finding Needle's existing
one. Two Claude sessions independently checked the two texts and found the same
missing candidates.

Card #54 did not claim to read project files: its table's 60-paragraph evidence
surface was the former global file, and its walk explicitly excluded project
files. It correctly filed this successor. The defect is in this successor's
present emphasis: it describes a project file first as duplicated doctrine to
remove. A session following that lens can classify a stronger, hard-earned rule
as a restatement and delete the evidence before the global text has learned
from it. Canon establishes authority, not completeness.

## Why it matters

The owner's intent is one doctrine every project follows, with project files
holding only what is that project's, **and every project's learning improving
that doctrine before its local copy is removed**. A project file that restates
a doctrine section is a second text by another name: when HOW-WE-WORK changes
on a card, the project's copy does not, and a session on that project reads the
older rule with the project's authority behind it. But resemblance is not
equivalence: a local rule may carry a discriminator, trigger or failure history
that makes it stronger than the global sentence. Deleting it as duplication
makes the one text tidier and the work less reliable. The table's row 3b
proposes the layering sentence for HOW-WE-WORK ("this document holds what is
true in every session, on every project; a project's own file holds the
rest"); this card is what makes that sentence true rather than aspirational in
both directions.

## Fix

The same instrument as #54, per project, but source-first: a table with one row
per paragraph of the project's `CLAUDE.md`. Each row has exactly one stance:

1. *the project's own* — legitimate domain truth or specialised method; stays;
2. *global wins* — HOW-WE-WORK carries the same intent at equal or greater
   strength; the local copy drops, with the comparison quoted;
3. *missing portable doctrine* — a rule every project needs, supported by an
   observed failure; it travels back through its own `Fix: his` suggestion
   before the local words are removed;
4. *portable intent wearing a project mechanism* — the intent travels and the
   local mechanism stays or drops with the project;
5. *method or causal story not established by its evidence* — surfaced as an
   unproved claim, never promoted because it sounds explanatory; or
6. *contested* — it contradicts the global text or the reader cannot establish
   which is stronger, so the owner receives both readings and neither is
   silently selected.

The first pass is over the file's words and its recorded failure histories,
not merely its Git age and not every implementation artefact it points to.
Hello Revenue's first candidate rows include the six verification/search
distinctions named in the observation above. Its general loop obligation is a
counterexample in the other direction: HOW-WE-WORK §7 is stronger even though
Hello Revenue has practised at least one falsifiable loop locally. The owner
rules on the table; portable learnings land in HOW-WE-WORK before a project
edit removes their source.

Then a reader: a ratchet in each project, or one on the board, that refuses a
project-file paragraph whose sentence HOW-WE-WORK already carries **only after
the ruled table has established global-wins equivalence**. A lexical overlap is
not proof: it would mechanise the subtractive lens and erase sharper rules.
Hello Revenue first (the richest known source as well as the largest file),
Needle second, the machine repo's own `CLAUDE.md` third.

## Boundary that must not change

A project's legitimate specifics survive untouched: Hello Revenue's twelve quality intents and its method register, Needle's typed edges and "the board never runs", the machine's one rule that the file in the repo is the live file. The table's third stance exists so that "consolidate" never reads as "flatten".
